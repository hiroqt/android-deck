# MacDeck --- Architecture

## 1. Architectural Intent

MacDeck is a local, two-application system:

1.  **Android Deck Client** --- renders controls, captures touch events,
    provides haptics, displays Mac state.
2.  **macOS Host Agent** --- owns trust, configuration, action
    execution, permissions, system observation, and persistence.

The phone is intentionally a thin control surface. The Mac is the
authority.

``` text
┌──────────────────────────┐
│ Android Deck Client      │
│ Kotlin + Jetpack Compose │
│                          │
│ UI / Haptics / State     │
│ WebSocket Client         │
└────────────┬─────────────┘
             │
      USB/ADB or LAN
             │
      Persistent WebSocket
             │
┌────────────▼─────────────┐
│ macOS Host Agent         │
│ Swift + SwiftUI/AppKit   │
│                          │
│ Session/Auth             │
│ Protocol Router          │
│ Profile Manager          │
│ Action Registry          │
│ Permission Manager       │
│ System Observers         │
│ Persistence/Keychain     │
└────────────┬─────────────┘
             │
   ┌─────────┼───────────────┐
   ▼         ▼               ▼
NSWorkspace  CoreGraphics    Process /
AppKit       Automation      AppleScript /
                            Shortcuts
```

This follows the project direction established in the source discussion:
Kotlin/Compose on Android, Swift on macOS, a persistent WebSocket,
ADB/USB transport, Mac-owned action execution, and a generic protocol
rather than hard-coded buttons.

## 2. Technology Decisions

### Android

-   Kotlin
-   Jetpack Compose
-   Coroutines + Flow
-   OkHttp WebSocket
-   kotlinx.serialization
-   DataStore for non-secret preferences
-   Android Keystore-backed secret storage
-   MVVM/unidirectional state flow

### macOS

-   Swift
-   SwiftUI for settings/menu-bar UI
-   AppKit/NSWorkspace for application integration
-   URLSession WebSocket or Network.framework-compatible WebSocket layer
-   CoreGraphics/Accessibility APIs for approved input/window actions
-   `Process` for registered scripts
-   AppleScript/Shortcuts adapters where useful
-   Keychain for device credentials
-   Codable for protocol/config models

### Persistence

Start with JSON/Codable files for profiles and actions because the model
is small and human-debuggable. Introduce SQLite only if querying,
migrations, history, or large plugin state make it necessary.

## 4. Runtime Components

### Android UI layer

Responsibilities: - Render server-provided profiles. - Capture
tap/long-press/double-tap/slider events. - Apply immediate pressed-state
feedback. - Trigger optional haptics. - Show connection state. - Never
execute Mac commands itself.

### Android connection manager

State machine:

``` text
DISCONNECTED
    ↓
CONNECTING
    ↓
AUTHENTICATING
    ↓
SYNCING
    ↓
READY
    ↓
RECONNECTING ─────────────┐
    └─────────────────────┘
```

Responsibilities: - WebSocket lifecycle. - Heartbeats. -
Authentication. - Request IDs. - Retry/backoff. - Profile/state
resynchronization.

### Mac WebSocket server

Responsibilities: - Accept local connections. - Enforce payload
limits. - Parse versioned envelopes. - Authenticate before action
messages. - Route messages. - Keep action execution off the networking
loop.

### Pairing/Auth service

First pairing:

``` text
Android -> pair.request
Mac displays 6-digit code
User confirms/enters code
Android -> pair.confirm
Mac -> device token
Both persist trust
```

The 6-digit code is only a human verification mechanism. The durable
credential is a random token generated by the Mac.

### Profile manager

Owns: - Profile definitions. - Active profile. - Page/control layout. -
App-to-profile rules. - Profile revision/version.

Android caches the most recent profile for fast startup, but the Mac
remains authoritative.

### Action registry

Interface concept:

``` swift
protocol DeckActionHandler {
    var type: ActionType { get }
    func validate(_ action: RegisteredAction) throws
    func execute(_ action: RegisteredAction, context: ActionContext) async throws -> ActionResult
}
```

Handlers: - LaunchAppAction - OpenURLAction - KeypressAction -
MediaAction - VolumeAction - ShortcutAction - RegisteredScriptAction -
WindowAction - SystemAction

### Permission manager

Maps actions to macOS capabilities and reports: - granted - denied -
notDetermined - unavailable

An action must fail with a typed error rather than silently doing
nothing.

### System observers

Observe: - Foreground application. - Selected system/media state where
supported. - Connection/transport status.

Foreground-app events feed the profile manager.

## 5. Transport Architecture

### Development/LAN

``` text
Android : ephemeral client port
       │
       │ ws://<mac-local-ip>:8765
       ▼
MacDeck Agent :8765
```

LAN mode is easiest for early development.

### USB production path

Use ADB TCP forwarding so the same application protocol is reused.

Recommended direction:

``` text
Android app -> localhost:<devicePort>
                     │
                     │ ADB reverse/forward tunnel
                     ▼
              Mac localhost:8765
```

The exact `adb forward` vs `adb reverse` direction must be selected and
tested against which side owns the listening socket. Do not duplicate
the protocol for USB; only replace the transport path.

### Transport abstraction

Android:

``` text
DeckTransport
├── LanWebSocketTransport
└── UsbWebSocketTransport
```

The application layer must not care which transport is active.

## 6. Protocol

Use JSON for v1 because it is inspectable and easy to debug. Every
message uses an envelope.

``` json
{
  "protocolVersion": 1,
  "type": "action.invoke",
  "requestId": "uuid",
  "timestamp": 1780000000000,
  "payload": {}
}
```

Core messages:

``` text
hello
auth.challenge
auth.authenticate
auth.accepted
pair.request
pair.challenge
pair.confirm
pair.accepted
profile.get
profile.snapshot
profile.changed
action.invoke
action.result
state.snapshot
state.changed
ping
pong
error
```

Example action invocation:

``` json
{
  "protocolVersion": 1,
  "type": "action.invoke",
  "requestId": "e2e7...",
  "payload": {
    "controlId": "dev-vscode",
    "event": "tap"
  }
}
```

Notice that the Android client does **not** send `/Applications/...`,
shell source, or arbitrary AppleScript.

Mac resolves:

``` json
{
  "controlId": "dev-vscode",
  "binding": {
    "actionId": "open-vscode"
  }
}
```

to a local registered action:

``` json
{
  "id": "open-vscode",
  "type": "launch_app",
  "parameters": {
    "bundleId": "com.microsoft.VSCode"
  }
}
```

## 7. Ordering and Idempotency

Every invocation gets a UUID request ID.

Rules: - UI taps are normally at-most-once from the client
perspective. - Client must not blindly replay non-idempotent actions
after reconnect. - Duplicate request IDs within a short server cache
window return the previous result where possible. - State/profile
messages carry monotonically increasing revisions. - Android ignores
stale revisions.

## 8. Threading and Concurrency

### Android

-   Compose on main thread.
-   Network parsing on background coroutine dispatcher.
-   State exposed through `StateFlow`.
-   Haptic/pressed feedback occurs immediately.
-   Network acknowledgement updates success/error state asynchronously.

### macOS

-   WebSocket receive loop must never run shell/automation work
    synchronously.
-   Parse/validate quickly, then dispatch to an action executor.
-   UI state changes run on MainActor.
-   Action handlers are async and isolated from each other where
    appropriate.
-   Long-running registered scripts need timeout/cancellation.

## 9. Security Boundaries

Trust boundary:

``` text
UNTRUSTED / LESS TRUSTED                TRUSTED
Android UI / LAN input                  Mac action registry
          │                                      │
          └──── validate/authenticate ───────────┘
```

Rules: 1. No arbitrary command strings. 2. No unauthenticated action
execution. 3. Device token required after pairing. 4. Tokens stored in
Keychain/Keystore. 5. Per-device revocation. 6. Maximum message size. 7.
Schema validation. 8. Allowlisted URL schemes if `open_url` is enabled.
9. Registered scripts use Mac-side IDs. 10. Script arguments are either
fixed or validated against declared parameter types. 11. Logs redact
credentials. 12. LAN server is not intended for internet exposure.

## 11. Failure Modes

  -----------------------------------------------------------------------
  Failure                             Expected behavior
  ----------------------------------- -----------------------------------
  USB unplugged                       Android enters reconnecting; may
                                      fall back to LAN if enabled

  Mac agent stopped                   Android retains cached UI but
                                      disables/marks execution
                                      unavailable

  Wi-Fi changes                       reconnect/backoff

  Permission missing                  typed action failure + Mac
                                      permission guidance

  App missing                         action failure, no crash

  Unknown action                      reject

  Invalid token                       disconnect/re-pair

  Profile malformed                   keep last known good profile

  Script timeout                      terminate if configured, return
                                      timeout

  Protocol mismatch                   show incompatible-version state
  -----------------------------------------------------------------------

## 12. Observability

Both apps should use structured logs with: - timestamp - subsystem -
event - request ID - device ID hash - duration - result/error code

Never log tokens or pairing codes.

Useful metrics during development: - tap-to-send - send-to-receive -
server validation - action execution - result return - total round-trip
